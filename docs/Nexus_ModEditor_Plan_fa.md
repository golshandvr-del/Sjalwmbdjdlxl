### Project Nexus — افزودن ویرایشگر گرافیکی ماژولار (نیرو / ساختمان / نقشه / آبجکت)

> نسخه: ۱.۰ | تاریخ تنظیم: ۲۰۲۶-۰۶-۲۶
> این سند بر اساس **تحلیل کد واقعی نسخه‌ی `project-nexus_2026-06-26_phaseE`** نوشته شده،
> نه به‌صورت عمومی. هر جا گفته می‌شود «هست/نیست»، یعنی در همان فایل‌های واقعی پروژه بررسی شده است.

## ۰. خلاصه‌ی مدیریتی (TL;DR)

ایده‌ی تو **عالی، منسجم و کاملاً قابل‌اجرا** است — و مهم‌تر اینکه با معماری فعلی پروژه (Central Brain / Data-Driven / `.nexpack`) **هم‌خوان** است. تو در واقع داری یک «ابزار تولید محتوای بازی» (Content Authoring Tool) طراحی می‌کنی که خروجی‌اش همان JSONهایی است که موتور همین الان می‌خواند.

اما سه نکته‌ی کلیدی:

1. **بخشی از زیرساختش از قبل آماده است.** پروژه همین الان `ModProject`، `ScenarioProject`، صحنه‌ی `mod_editor.tscn`، `map_editor.tscn` و فرمت پکیج `.nexpack` را دارد. تو از صفر شروع نمی‌کنی؛ تو داری یک هسته‌ی ساده را به یک ادیتور کامل **ارتقا** می‌دهی.
2. **شکاف اصلی، عمقِ schema و UI است، نه معماری.** ادیتور فعلی فقط `health`/`cost`/`color` را با چند اسلایدر ویرایش می‌کند. چیزی که تو می‌خواهی (نمودار درختی، چندبخشی، تب‌های ارتقا/تعلیم، گرافیک پیکسلی، آبجکت دریا/خشکی، اصلاح ساحل) **هیچ‌کدام هنوز پیاده نشده** و باید ساخته شود.
3. **چند قانون طراحی تو نیاز به دقیق‌سازی دارد** تا با ماهیت قطعی (Deterministic) و چندنفره‌ی بازی نشکند — مفصل در بخش ۲ توضیح داده‌ام.

## ۱. نقد و بررسی فنی ایده

### ۱.۱ نقاط قوت ایده ✅

- **هم‌راستا با data-driven بودن موتور:** بازی همین الان نیرو/ساختمان/سناریو را از JSON می‌خواند (`data/units/*.json`, `data/buildings/*.json`, `data/scenarios/*.json`). ادیتور تو فقط باید همان JSONها را تولید کند → **بدون یک خط تغییر در موتور**، محتوای ساخته‌شده قابل‌بازی می‌شود. این دقیقاً همان چیزی است که مودِ `playdough_demo` ثابت کرده.
- **ساختار «هسته‌ی خام + درخت»:** ایده‌ی «نیروی خام / ساختمان خام» به‌عنوان ریشه، یک الگوی **inheritance/template** زیبا است. هر بلوک فرزند می‌تواند فیلدهای والد را به ارث ببرد و فقط تفاوت‌ها را بازنویسی کند → حجم داده کم، نگه‌داری آسان.
- **تفکیک «تک‌بخشی / چندبخشی»:** این یک تصمیم معمارانه‌ی درست است. چندبخشی بودن، پایه‌ی دو مکانیک عمیق توست: **ترکیب نیروها** و **تخریب مستقل اجزای ساختمان**. این دو، عمق گیم‌پلی واقعی می‌سازند.
- **قانون «۱۵٪ سقف افزایش ابعاد در ارتقا»:** هوشمندانه است — جلوی خراب‌شدن بالانس بصری و برخورد (collision) را می‌گیرد.
- **`Object Editor` با «قابل استخراج + متریال خروجی»:** این آبجکت‌ها را از صرفِ تزئین به **منبع اقتصادی** تبدیل می‌کند و به سیستم economy موجود وصل می‌شود.

### ۱.۳ ناسازگاری‌های کوچک با کد فعلی (باید آگاه باشی)

- **ادیتور فعلی فقط دو کاتالوگ UI دارد** (units, buildings) و آن هم با اسلایدر ساده. درخت، تب‌بندی، و آپلود تصویر در UI **نیست** و باید کامل نوشته شود.
- **`ScenarioProject` فقط `wall`/`ground` دارد** — مفهوم «دریا/خشکی/ساحل» و «object قابل‌استخراج» در آن نیست و باید افزوده شود.
- **«Object Editor» اصلاً وجود ندارد** — نه مدل، نه UI، نه کاتالوگ. کاملاً جدید است.
- **مدل چندبخشی (multi-part) وجود ندارد** — `default_unit`/`default_building` فقط تک‌بخشی و تخت هستند.

### ۱.۴ جمع‌بندی نقد

ایده **پذیرفته و تأیید می‌شود**، با این چارچوب طلایی که در کل فازبندی رعایت می‌شود:

> **اصل طلایی #۱ (Cosmetic vs Logic):** هر چیزی که «ظاهر/پیکسل/تصویر/رنگ» است → فقط بصری، روی هش قطعی اثر ندارد. هر چیزی که «stat/cost/قابلیت/اندازه‌ی منطقی» است → داده‌ی شبیه‌سازی، قطعی.
> **اصل طلایی #۲ (Tooling-only):** ادیتور هیچ‌وقت به `WorldState` یا هش دست نمی‌زند؛ فقط *داده تولید می‌کند*. (دقیقاً مثل `ModProject`/`ScenarioProject` فعلی.)
> **اصل طلایی #۳ (Validate-before-save):** هیچ پکِ نامعتبری ذخیره نمی‌شود؛ هر ورودی نامعتبر با دلیل رد می‌شود.
> **اصل طلایی #۴ (English-only code):** طبق `CODE_POLICY`؛ تمام متن‌های دیداری فقط از طریق `localization/` (کلید انگلیسی → متن فارسی).

## ۲. تصمیم‌های طراحی پیش از فازبندی (قراردادهای داده)

برای اینکه فازها قابل‌اجرا و بدون شکستن determinism باشند، این قراردادها را قبل از کد قطعی می‌کنیم:

### ۲.۱ مدل درخت (Tree Model)
به هر تعریف (unit/building/object) دو فیلد متادیتای ادیتور اضافه می‌شود (موتور بازی آن‌ها را نادیده می‌گیرد):
```jsonc
"editor": {
  "parent_id": "root_unit",   // ریشه: "root_unit" / "root_building" / "root_object"
  "tree_order": 3             // ترتیب نمایش بین هم‌سطح‌ها
}
```
- ریشه‌ها مجازی‌اند (در JSON ذخیره نمی‌شوند): `root_unit`, `root_building`, `root_object`.
- «افزودن زیرمجموعه» = ساخت فرزند با `parent_id = <selected>`.
- «افزودن هم‌سطح» = ساخت فرزند با `parent_id = <parent of selected>`.
- وراثت (اختیاری فاز پیشرفته): فرزند می‌تواند فقط فیلدهای متفاوت را override کند.

### ۲.۲ مدل گرافیک پیکسلی (Pixel Graphics)
```jsonc
"graphic": {
  "mode": "single",            // "single" | "multi"
  "logical_size": { "w": 1, "h": 1 },   // اندازه‌ی منطقی (tile) — روی هش اثر دارد
  "parts": [                   // single = یک عنصر، multi = حداکثر ۳ عنصر
    { "layer": 1, "px": {"w":64,"h":64}, "texture": "textures/u_base.png" },
    { "layer": 2, "px": {"w":48,"h":48}, "texture": "textures/u_mid.png"  },
    { "layer": 3, "px": {"w":32,"h":32}, "texture": "textures/u_top.png"  }
  ]
}
```
- قانون لایه‌بندی: `px(layer3) ≤ px(layer2) ≤ px(layer1)` — اعتبارسنجی در مدل.
- فرمت مجاز: `PNG` فقط. رزولوشن مجاز: حداقل `16×16`، حداکثر `512×512` (قابل‌تنظیم، زیر باکس آپلود نمایش داده می‌شود).
- **پیکسل‌ها فقط بصری‌اند؛** `logical_size` چیزی است که برخورد/شبکه استفاده می‌کند (اصل طلایی #۱).

### ۲.۳ مدل مشخصات (Stats / Attributes) و سازگاری
- هر stat یک «تعریف» در یک رجیستری دارد: `id`, `needs_value` (bool), `applies_to` (unit/building/both), `group`.
- نمونه گروه‌ها: `combat` (damage, fire_rate, range), `defense` (hp, armor), `mobility` (move_speed), `economy` (extraction_rate), `vision`.
- **جدول سازگاری چندبخشی:** statهای یک گروه نمی‌توانند هم‌زمان در دو بخش فعال باشند (مثلاً دو بخش هر دو `extraction_rate` نداشته باشند). ادیتور گزینه‌های ناسازگار را disable می‌کند.
- **ساختمان چندبخشی:** هر بخش **اجباراً** `hp` + `armor` دارد (طبق خواست تو)؛ این در validate چک می‌شود.

### ۲.۴ مدل ارتقا (Upgrade)
```jsonc
"upgrade": {
  "trigger": { "type": "tech_node|kill_count|time_ticks|activity", "value": 50, "ref": "tech_x" },
  "effects": { "stat_add": {...}, "stat_mul": {...}, "add_ability": [...] },
  "visual_change": { "part": 1, "texture": "textures/u_lvl2.png", "px": {"w":72,"h":72} }
}
```
- قانون: ابعاد جدیدِ بخش پایه (layer 1) حداکثر `+15%` نسبت به اصل (سقف سخت در validate).

### ۲.۵ مدل تعلیم/تکنولوژی ساخت (Train / Build Tech)
```jsonc
"buildable": {
  "from_building": "barracks",     // dropdown از ساختمان‌های تعریف‌شده (units)
  "cost": { "resource_basic": 50, "material_x": 10 },
  "materials": ["material_x"],     // ساختمان چندبخشی: متریال لازم
  "required_tech": "tech_node_id"  // dropdown از techهای تعریف‌شده
}
```

### ۲.۶ مدل آبجکت نقشه (Map Object)
```jsonc
{ "id": "iron_rock", "graphic": {...}, "logical_size": {...},
  "placement": "land|sea|both",
  "extractable": true,
  "yields": { "material": "iron", "rate": 2 } }
```

### ۲.۷ مدل زمین نقشه (Map Terrain)
- توکن‌های منطقی: `land`, `sea`, `wall` (دیوار از قبل هست).
- **ساحل (beach/coast) داده‌ی ذخیره‌شده نیست** → فقط در رندر با autotile bitmask از روی همسایه‌ها محاسبه می‌شود (اصل طلایی #۱، ریسک R5).

## ۳. فازبندی اجرایی (Phase E2 → E6)

> فازها ادامه‌ی شماره‌گذاری موجود پروژه‌اند. فاز فعلی E (هسته‌ی scenario) انجام شده؛
> این‌ها فازهای **E2 تا E6** هستند. هر فاز با تست headless تمام می‌شود (مثل بقیه‌ی پروژه).

---

### فاز E2 — زیرساخت مشترک ادیتور (Tree + Graphic + Stats Registry)
**هدف:** ستون فقراتی که هر سه ادیتور (نیرو/ساختمان/آبجکت) روی آن سوار می‌شوند.

- **E2.1 — مدل درخت در `ModProject`/`ScenarioProject`**
  افزودن متادیتای `editor.parent_id` + `tree_order`؛ توابع `add_child(parent_id)`, `add_sibling(node_id)`, `rename_node`, `build_tree()` (خروجی ساختار درختی برای UI).
- **E2.2 — رجیستری ویژگی‌ها (`tools/stat_registry.gd`)**
  تعریف همه‌ی statها با `needs_value`/`applies_to`/`group`؛ تابع `compatible(part_a_stats, part_b_stats)` برای جدول سازگاری.
- **E2.3 — مدل گرافیک + اعتبارسنجی تصویر (`tools/graphic_model.gd`)**
  ساختار `graphic{mode,logical_size,parts}`؛ توابع `validate_layer_sizes()`, `validate_image(bytes, fmt, min, max)`.
- **E2.4 — سرویس بسته‌بندی تصویر** اتصال به `add_texture()` موجود؛ ذخیره‌ی `PackedByteArray` در پک + ساخت نام یکتا.
- **E2.5 — کلیدهای localization** افزودن همه‌ی کلیدهای جدید UI به `en.json` + `fa.json` (tree, tabs, graphic, stats, upgrade, train).
- **E2.6 — تست‌های headless E2** درخت round-trip، رد تصویر نامعتبر، تشخیص تداخل ویژگی، سقف لایه‌ها.

---

### فاز E3 — ویرایشگر نیرو (Unit Editor) کامل
**هدف:** پیاده‌سازی کامل سناریوی «یک) الف/ب» تو.

- **E3.1 — UI نمودار درختی نیرو** بلوک مرکزی «نیروی خام»، منوی راست‌کلیک/کلیک: ویرایش نام / ساخت / افزودن زیرمجموعه / افزودن هم‌سطح.
- **E3.2 — صفحه‌ی انتخاب «تک‌بخشی / چندبخشی»** با توضیح «تک‌بخشی قابل ترکیب نیست».
- **E3.3 — تب اصلی (تک‌بخشی):** گرافیک (ابعاد پیکسل + یک تصویر + نمایش فرمت/رزولوشن مجاز) + انتخاب پویا‌ی مشخصات (فقط statهای انتخاب‌شده فیلد می‌گیرند).
- **E3.4 — تب اصلی (چندبخشی):** ۳ بخش لایه‌ای با قانون اندازه، تصویر هر بخش، مشخصات هر بخش با چک تداخل، پرچم «قابل‌ترکیب».
- **E3.5 — تب ارتقا:** trigger (دستاورد/کشته/زمان) + effects + visual_change + سقف ۱۵٪.
- **E3.6 — تب تعلیم:** from_building (dropdown) + cost + required_tech (dropdown).
- **E3.7 — ذخیره** نوشتن تعریف نیرو در کاتالوگ units + بسته‌بندی تصاویر.
- **E3.8 — تست‌های headless E3** ساخت نیروی تک/چندبخشی معتبر، رد چندبخشیِ دارای تداخل، round-trip.

---

### فاز E4 — ویرایشگر ساختمان (Building Editor) کامل
**هدف:** سناریوی «دو) الف/ب» — مشابه نیرو با تفاوت‌ها.

- **E4.1 — اشتراک UI درخت/تب با نیرو** بازاستفاده از E3 با کاتالوگ buildings.
- **E4.2 — تب اصلی تک‌بخشی:** گرافیک + مشخصات (شامل `extraction_rate` برای ساختمان منبع).
- **E4.3 — تب اصلی چندبخشی:** هر بخش **اجباراً hp+armor**؛ تخریب مستقل اجزا (داده‌ی `part_destructible: true`).
- **E4.4 — تب ارتقا** (شامل trigger «مقدار فعالیت» مخصوص ساختمان) + سقف ۱۵٪.
- **E4.5 — تب تکنولوژی ساخت:** cost + materials + required_tech (dropdown).
- **E4.6 — ذخیره + تست‌های headless E4** (اجبار hp/armor در هر بخش، تخریب مستقل، round-trip).

---

### فاز E5 — ویرایشگر آبجکت (Object Editor)
**هدف:** بخش «object» مپ‌ادیتور.

- **E5.1 — کاتالوگ جدید `objects`** در `ModProject` + ریشه‌ی درخت `root_object`.
- **E5.2 — UI درختی آبجکت** (همان ساختار بلوکی نیرو/ساختمان).
- **E5.3 — فرم آبجکت:** نام، ابعاد، تصویر، نوع placement (دریا/خشکی/هردو)، extractable، yields (متریال خروجی).
