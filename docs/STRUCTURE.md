# سند ساختار و نقشه‌ی راه — Project Nexus
### تک سند مرجع (Single Source of Truth) برای معماری، وضعیت، و فازبندی

> **نسخه‌ی سند:** ۲.۰ | **نسخه‌ی هدف بازی:** `0.6.0` | **تاریخ:** ۲۰۲۶
> **پلتفرم اولویت:** Android (`armeabi-v8a`) → iOS → Windows/macOS/Linux
> **موتور:** Godot 4.x (GDScript؛ C++/GDExtension فقط برای hot-pathها در آینده)
>
> این سند بر اساس **تحلیل کد واقعی پروژه** نوشته شده. از این نسخه به بعد، این
> فایل **تنها سند مرجع فازبندی** است؛ سندهای پراکنده‌ی قبلی
> (`Nexus_ModEditor_Plan_fa.md`) در همین فایل ادغام شدند (بخش ۹).
>
> **مخاطب این سند:** توسعه‌دهنده/AI بعدی. هدف این است که کسی که این را می‌خواند
> **بدون خواندن دوباره‌ی کل کد** بفهمد چه چیزی ساخته شده، چه چیزی خراب است، و
> دقیقاً چه باید بسازد. برای نقشه‌ی سریع کد به `docs/CODE_MAP.md` مراجعه کن.

## ۰. چطور این سند را بخوانیم (راهنمای خواننده)

اگر AI/توسعه‌دهنده‌ای هستی که تازه به پروژه رسیده‌ای، به این ترتیب بخوان:

1. **بخش ۱** — معماری در یک نگاه (چرا همه‌چیز از EventBus/WorldState می‌گذرد).
2. **بخش ۲** — چه چیزی از قبل ساخته شده (تا دوباره‌کاری نکنی).
3. **بخش ۳ — 🔴 بحرانی: باگ‌های شناخته‌شده با ریشه‌یابی دقیق** (این‌ها اولویت
   نسخه ۰.۶.۰‌اند؛ ریشه‌ی هر باگ در کد مشخص شده).
4. **بخش ۴** — خواسته‌های نسخه ۰.۶.۰ به‌صورت **مرتب‌شده و بدون‌ابهام** (این همان
   چیزی است که کاربر می‌خواهد؛ با دقت بخوان چون AIهای قبلی اینجا اشتباه فهمیدند).
5. **بخش ۵ تا ۸** — فازبندی اجرایی (`P0`…`P9`) با معیار پذیرش هر فاز.
6. **بخش ۹** — قراردادهای داده (schemaها) که نباید بشکنند.
7. **بخش ۱۰** — اصول طلایی ثابت پروژه (این‌ها را هرگز نقض نکن).

> ⚠️ **هشدار به AI بعدی (چرا نسخه‌های قبل شکست خوردند):** AIهای قبلی فقط لایه‌ی
> **مدل headless** مود ادیتور را ساختند (در `tools/mod_project.gd`) و README را
> «انجام‌شد» علامت زدند، **ولی UI واقعی را وصل نکردند**. کاربر وقتی بازی را باز
> کرد، هنوز فقط سه فیلد `hp/cost/color` دید. **درسِ کلیدی: «مدل ساخته‌شد» ≠
> «کاربر می‌تواند استفاده کند».** معیار پذیرش هر فاز در این سند = *کاربر روی
> دستگاه واقعی آن را ببیند و استفاده کند*، نه اینکه فقط تست headless سبز شود.

## ۱. معماری در یک نگاه — «مغز مرکزی» (Nexus)

Nexus **خودش هیچ گیم‌پلی‌ای ندارد**؛ فقط هماهنگ‌کننده است. اجزای هسته در `core/`:

| جزء | فایل | مسئولیت |
|---|---|---|
| **Nexus** | `core/nexus.gd` | Autoload؛ همه‌چیز را سیم‌کشی و حلقه‌ی tick را می‌راند |
| **EventBus** | `core/event_bus.gd` | ارتباط pub/sub غیروابسته |
| **WorldState** | `core/world_state.gd` | تنها منبع حقیقت (بخش‌های سریال‌پذیر) |
| **ModuleRegistry** | `core/module_registry.gd` | چرخه‌ی حیات ماژول (init/tick/event/shutdown) |
| **SimClock** | `core/sim_clock.gd` | ساعت tick قطعی + Active Pause |
| **CommandQueue** | `core/command_queue.gd` | فرمان‌های بازیکن/AI (پایه‌ی lockstep) |
| **DataLoader** | `core/data_loader.gd` | بارگذاری محتوای داده‌محور (JSON + مود) |
| **SaveSystem** | `core/save_system.gd` | سریال/بازیابی کل بازی به JSON |
| **StateHasher** | `core/state_hasher.gd` | checksum قطعی WorldState (تشخیص desync) |
| **ModLoader** | `core/mod_loader.gd` | کشف/بارگذاری مود (پوشه + `.nexpack`) |
| **StorageService** | `core/storage_service.gd` | ریشه‌ی محتوای قابل‌تنظیم |
| **Pack{Format,Reader,Writer}** | `core/pack_*.gd` | فرمت پکیج `.nexpack` (ZIP) |
| **TextureService** | `core/texture_service.gd` | کش `texture_id → Texture2D` چند‌ریشه‌ای |
| **Localization** | `core/localization.gd` | کلید انگلیسی → متن محلی (en/fa) |
| **GameSettings** | `core/game_settings.gd` | تنظیمات ماندگار |

**قانون طلایی #۰:** هیچ ماژولی ماژول دیگر را مستقیم صدا نمی‌زند. همه‌چیز از
`Nexus.event_bus` و `Nexus.world_state` می‌گذرد.

### ۱.۱ جریان یک فرمان (مثلاً «حرکت نیرو»)
```
لمس کاربر (game_hud.gd)
  → Nexus.issue_command("move_unit", owner, {unit_ids, x, y}, delay)
  → CommandQueue (روی tick اجرا می‌شود؛ در مولتی‌پلیر: بعد از input_delay)
  → EventBus: "command.move_unit"
  → UnitsModule.handle_event() → مسیر A* را حساب و در unit["path"] می‌ریزد
  → on_tick: هر چند tick یک قدم بر می‌دارد (قطعی)
  → EventBus: "units.moved"
  → RenderAdapter (فقط می‌خواند و رسم می‌کند؛ هرگز نمی‌نویسد)
```

### ۱.۲ معماریِ AIِ داده‌محور (دورِ MD — `docs/plan_android_fix_v4.md`)

دورِ MD یک **بازمعماریِ بنیادین** است (نه رفعِ باگ): AI دیگر به نامِ واحد یا
statِ خام گره نخورده، بلکه روی یک **زنجیره‌ی داده‌محورِ کاملاً قطعیِ fixed-point**
تصمیم می‌گیرد. این تضمین می‌کند که (۱) هر مود بدونِ یک خطِ کدِ موتور کار کند و
(۲) کلاینت‌های lockstep روی ARM/x86 هم‌گام بمانند.

```
stat خام (data) → affects → Capability(بردار fixed-point) → Role
     → [AiProfile → وزنِ نقش/capability] → Context → Policy
     → Utility Scoring → تصمیمِ مرحله‌ای → Command → Learning
```

- **دو لایه:** (۱) **Stat به‌عنوان Data** (نه hard-code؛ Core Stat در برابر Free/Mod
  Stat) و (۲) **خطِ لوله‌ی تصمیمِ چندلایه‌ی AI**. جزئیاتِ فایل‌به‌فایل و نمودارِ کامل
  در `docs/CODE_MAP.md` بخشِ «۲.۵ خطِ لوله‌ی تصمیمِ AI».
- **قانونِ طلایی:** هیچ float در مسیرِ تصمیمی که روی `state_hasher` اثر دارد نمی‌ماند؛
  همه‌چیز `[0..SCALE=1000]`، مرتب‌سازیِ پایدار بر id، گِردکردنِ round-half-away-from-zero.
- **Capability = قراردادِ بسته و نسخه‌دار (۱۷ توانایی):** مود **مقدارِ** capability را
  از راهِ stat/affects عوض می‌کند، هرگز **فهرست** را. AI فقط Capability+Role را می‌بیند.
- **جداییِ cosmetic/simulation:** نمایشِ UIِ metric/role هرگز به sim hash دست نمی‌زند؛
  هر اثرِ رفتاری از راهِ Command می‌رود.
- **تابِ‌آوری:** statِ غایب → `default_q`؛ بردارِ ناقص → نقشِ `generic`؛ context/policy/
  نامزدِ خالی → اکشنِ SAFE؛ هرگز crash/RNGِ بی‌seed.

## ۳. 🔴 باگ‌های شناخته‌شده (ریشه‌یابی از کد واقعی)

این‌ها گزارش مستقیم کاربر از بازی نصب‌شده‌اند. هرکدام با محل دقیق در کد و علتِ
ریشه‌ای آمده تا AI بعدی وقت را صرف پیدا کردن نکند. **رفع این‌ها اولویت #۱ نسخه است.**

### BUG-1 — رشد انفجاری resource از ابتدای بازی
- **محل:** `modules/economy/economy_module.gd::on_tick()` +
  `data/buildings/hq.json → produces: {resource_basic: 2}`.
- **علت ریشه‌ای:** تولید منابع **per-tick** است، نه per-second. `SimClock` با
  نرخ بالا (و ضریب سرعت ۱x/۲x/۴x) تیک می‌زند، پس «۲ در هر تیک» یعنی ده‌ها واحد
  در ثانیه. با `time_scale` بالاتر، بدتر می‌شود.
- **راه‌حل موردنظر:** تولید را به **نرخ زمان‌مبنا** ببر: یک شمارنده‌ی
  `production_interval_ticks` (مثلاً هر ۳۰ تیک یک‌بار `produces` اعمال شود)، یا
  فیلد `produces_per_seconds`. باید **قطعی** بماند (بر پایه‌ی `current_tick`، نه
  `delta` واقعی). مقدارِ اولیه‌ی منطقی: چند واحد در ثانیه، نه در تیک.

### BUG-2 — نیروی جدید روی HQ اسپاون می‌شود (تداخل با ساختمان و نیروهای دیگر)
- **محل:** `modules/buildings/buildings_module.gd` (هندلر `queue_unit` →
  فراخوانی `units.spawn_unit(type, owner, x, y)` با مختصات خود HQ).
- **علت ریشه‌ای:** هیچ منطق «یافتن سلول آزاد مجاور» یا نقطه‌ی rally وجود ندارد؛
  نیرو دقیقاً روی سلول ساختمان می‌نشیند و روی هم انباشته می‌شود.
- **راه‌حل موردنظر:** هنگام اسپاون، از تابع تازه‌ی `find_free_spawn_tile(building)`
  استفاده شود که به‌صورت مارپیچی/BFS نزدیک‌ترین سلولِ walkable و **خالی** (بدون
  نیرو/ساختمان) اطراف ساختمان را پیدا کند. اگر کاربر «نقطه‌ی rally» تعیین کرده
  بود، نیرو بعد از اسپاون به آن نقطه move شود. اشغال‌بودن سلول باید قطعی چک شود.

### BUG-3 — نیروها حرکت نمی‌کنند (لمس کار نمی‌کند)
- **محل:** `ui/mobile/game_hud.gd::_handle_tap()` + `screen_to_tile()` در
  `render/render_adapter.gd`، و `data/units/*.json → move_speed` +
  `units_module.gd::_advance_movement()`.
- **علت‌های ریشه‌ای محتمل (باید هر سه بررسی شوند):**
  1. **تبدیل مختصات:** `_gui_input` موقعیت را در فضای `Control` می‌گیرد، ولی
     `RenderAdapter` زیر `WorldLayer` است. اگر `WorldLayer` آفست/مقیاس داشته باشد،
     `screen_to_tile()` سلولِ اشتباه بر می‌گرداند و فرمان move به سلول غلط می‌رود.
     → مختصات لمس باید به فضای محلی RenderAdapter تبدیل شود
     (`make_input_local` یا `RenderAdapter.to_local`).
  2. **cooldown حرکت:** `unit["move_cooldown"] = max(0, 3 - move_speed)`. با
     `move_speed = 2` → cooldown = ۱. این درست است، ولی اگر `move_speed` بزرگ
     باشد cooldown صفر و اگر مسیر خالی برگردد حرکتی رخ نمی‌دهد.
  3. **مسیر خالی:** اگر A* مقصد را ناوابسته/غیرقابل‌عبور بیابد،
     `_compute_path` فقط `[start]` بر می‌گرداند و بعد از `remove_at(0)` مسیر
     خالی می‌شود → نیرو تکان نمی‌خورد و هیچ بازخوردی به کاربر نمی‌دهد.
- **راه‌حل موردنظر:** رفع تبدیل مختصات (اولویت)، افزودن **بازخورد بصری** (مثلاً
  علامت مقصد/خط مسیر)، و مسیریابی به نزدیک‌ترین سلولِ قابل‌رسیدن اگر مقصد اشغال بود.

### BUG-4 — نبودِ zoom/pan تعاملی روی نقشه
- **محل:** `ui/mobile/game_hud.gd` (هیچ pinch/drag handler ندارد)؛
  `render_adapter.gd` فقط `fit_map_to_viewport` و `center_camera_on` دارد.
- **راه‌حل موردنظر:** افزودن کنترل لمسی:
  - **Pinch (دو انگشت)** → تغییر `zoom` حول نقطه‌ی میانی انگشت‌ها.
  - **Drag تک‌انگشتی روی زمینِ خالی** (نه روی نیرو) → pan (`camera_offset`).
  - دکمه‌های `+/−` هم برای دستگاه‌های تک‌لمسی.
  - محدوده‌ی zoom (`min/max`) و clamp کردن pan به مرزهای نقشه.
  - **مهم:** zoom/pan فقط `camera_offset`/`zoom` (cosmetic) را تغییر می‌دهد؛ هرگز
    WorldState را لمس نمی‌کند.

### BUG-5 — ظاهر بسیار ضعیف و «مسخره»
- **محل:** `render/style_simple/*` (پیش‌فرض)، نبود فونت اختصاصی، HUD بی‌روح.
- **راه‌حل موردنظر (فاز `P1`):**
  - سبک پیش‌فرض را به `sprite` (تکسچرمحور) ببر و تکسچرهای بهتر بساز.
  - یک **فونت اختصاصی** (مثلاً Vazirmatn برای فارسی + یک فونت لاتین خوانا) در
    `assets/fonts/` و یک `theme` سراسری Godot (`assets/theme/nexus_theme.tres`).
  - رنگ‌بندی/فاصله‌گذاری/گوشه‌های گرد یکنواخت روی همه‌ی دکمه‌ها؛ نوارهای HP رنگی؛
    سایه‌ی نیرو/ساختمان؛ حلقه‌ی انتخاب واضح.
  - **قید:** فونت/تم/تکسچر همه cosmetic‌اند و روی هش قطعی اثر ندارند.

### BUG-6 — مود ادیتور با خواسته‌ی کاربر کاملاً فرق دارد
- **محل:** `ui/shared/mod_editor.gd` (فقط hp/cost/color).
- **علت:** UI هرگز به مدل پیشرفته‌ی `mod_project.gd` (درخت/چندبخشی/تب/گرافیک/آبجکت)
  وصل نشد.
- **راه‌حل:** کل فاز `P6` به این اختصاص دارد — بازسازی کامل UI مود ادیتور دقیقاً
  مطابق بخش ۴.۷ (که خواسته‌ی کاربر را کلمه‌به‌کلمه ساختاربندی کرده).

## ۴. خواسته‌های نسخه ۰.۶.۰ — مرتب‌شده و بدون‌ابهام

> این بخش، متن پراکنده‌ی درخواست کاربر را به خواسته‌های **اتمی، شماره‌دار و
> بدون‌ابهام** تبدیل کرده. هر خواسته یک شناسه (`R#`) دارد که در فازبندی به آن ارجاع
> می‌شود. **AI بعدی باید این بخش را دقیق پیاده کند؛ اینجا همان‌جایی است که قبلاً
> اشتباه فهمیده شد.**

### ۴.۱ منوی شروع بازی (Start/Setup Menu) — `R1`
یک منوی پیکربندی مسابقه که در **دو حالت** ظاهر می‌شود:
- از دکمه‌ی **تک‌نفره** → دکمه‌ی اقدام نهایی: **Run**.
- از دکمه‌ی **چندنفره** → دکمه‌ی اقدام نهایی: **Host**.

فیلدهای منو:
- `R1.1` نام بازی (match name، متنی).
- `R1.2` انتخاب نقشه (dropdown/لیست کشویی از نقشه‌های نصب‌شده — از
  `ScenarioLoader.list_scenarios`).

- `R1.4` تعداد AIها.
- `R1.5` نوع بازی (game mode): `team` (تیم‌بندی) / `ffa` (free-for-all) /

- `R1.6` (فقط وقتی نقشه از پیش موقعیت HQ/flag دارد) امکان تعیین اینکه هر
  بازیکن/AI و هر flag کجا قرار گیرد (بخش ۴.۹ را ببین).

### ۴.۲ نوار درصد پیشرفت (Progress Bar) در همه‌جا — `R2`
هرجا کاربر باید منتظر بماند، **نوار درصد** نشان داده شود:
- `R2.1` هنگام Run/Host (بارگذاری/راه‌اندازی مسابقه).
- `R2.2` هنگام همگام‌سازی خودکار مود بین host و joinها (بخش ۴.۶).
- `R2.3` هر عملیات طولانی دیگر (load/save/import/export).

### ۴.۳ ذخیره/بارگذاری بازی (Save/Load) — `R3`

### ۴.۴ Export/Import برای saveها — `R4`

- `R4.2` واردکردن یک فایل save.

### ۴.۵ Export/Import برای کل قالبِ مودِ نصب‌شده روی بازی — `R5`

  `.nexpack` واحد (از `PackWriter` موجود).
- `R5.2` واردکردن یک `.nexpack` و فعال‌کردن آن.

### ۴.۶ منوی مولتی‌پلیر (فعلاً فقط LAN) — `R6`
- `R6.1` **Host:** منویی با یک **لیست بازیکن خالی** به اندازه‌ی تعداد بازیکنی که
  در منوی شروع (`R1.3`) انتخاب کرده؛ اسلات‌ها با اتصال بازیکنان پر می‌شوند.
- `R6.2` **Join:** صفحه‌ای با **کادر جستجو + آیکن ذره‌بین** که سرورهای host‌شده در
  LAN را کشف می‌کند؛ کلیک روی سرور یافت‌شده = پیوستن.
- `R6.3` **مدیریت تیم توسط host:** host می‌تواند بازیکنان/AIها را در تیم‌ها بچیند
  (مثلاً همه‌ی AIها یک تیم، یا ترکیب AI+انسان).
- `R6.4` **Ready:** همه باید Ready بزنند تا بازی شروع شود.
- `R6.5` **کمترین لگ ممکن:** مولتی‌پلیر روی هسته‌ی lockstep موجود
  (`modules/multiplayer/`) است؛ باید `input_delay` تطبیقی، فشرده‌سازی فرمان‌ها و
  حداقل bandwidth (فقط فرمان‌ها، نه state) داشته باشد.
- `R6.7` (وابسته به `R5`) کشف LAN از طریق UDP broadcast (بخش ۸، `P5`).

### ۴.۶.۱ همگام‌سازی خودکار مود بین Host و Joinها — `R7`
- هنگام شروع مسابقه، اگر بازیکنانِ join‌شده مودهای host را نداشته باشند، بازی
  **خودکار** تشخیص می‌دهد، مودِ لازم را از host **آپلود** و روی joinها **دانلود و
  اعمال** می‌کند — قبل از استارت، با **نوار درصد** (`R2.2`).
- روش: مقایسه‌ی hash فهرست مودهای فعال؛ اگر متفاوت بود، host پکِ `.nexpack` را از
  طریق transport به join می‌فرستد و join آن را در ریشه‌ی محتوا نصب و بارگذاری
  می‌کند. **باید قطعی بماند** (کاتالوگ یکسان روی همه = lockstep-safe).

### ۴.۷ 🔴 بازسازی کامل Mod Editor — `R8` (مهم‌ترین و بزرگ‌ترین بخش)

> این دقیقاً همان چیزی است که کاربر خواسته و باید **بی‌کم‌وکاست** ساخته شود. متنِ
> پرتکرارِ کاربر اینجا یک‌بار و تمیز آمده. ساختار سه بخشی: **ساختمان / نقشه /
> نیرو** (نقشه بحثش جداست → بخش ۴.۸).

#### ساختار مشترک درختی (برای نیرو و ساختمان و آبجکت) — `R8.0`
- هر بخش یک **نمودار درختی / نقشه‌ی ذهنی** دارد که مرکزش **هسته‌ی خام** است
  (`نیروی خام` / `ساختمان خام` / ریشه‌ی آبجکت).
- کاربر روی یک بلوک کلیک می‌کند و منو می‌بیند:
  **«ویرایش نام»، «ساخت»، «افزودن زیرمجموعه»، «افزودن هم‌سطح»**.
  - «افزودن زیرمجموعه» = فرزندِ بلوک انتخاب‌شده (`add_child`).
  - «افزودن هم‌سطح» = بلوک جدید در سطح والدِ بلوک انتخاب‌شده (`add_sibling`).
- بلوک جدید اول باید نام‌گذاری شود، بعد قابل «ساخت» است.

#### هنگام «ساخت» — انتخاب تک‌بخشی/چندبخشی — `R8.1`
یک صفحه با دو گزینه‌ی انحصاری: **«چند بخشی»** و **«تک بخشی»**.
توضیح روی صفحه: *«اگر تک‌بخشی انتخاب شود، نیرو/ساختمان قابل ترکیب نیست.»*

#### ۴.۷.۱ ویرایشگر نیرو (Unit) — `R8.2`
هر دو حالت (تک/چندبخشی) **سه تب** دارند: **اصلی / ارتقا / تعلیم**.

**تک‌بخشی — تب اصلی:**
- گرافیک: کاربر ابعاد نیرو را بر حسب **پیکسل** وارد می‌کند و **یک** تصویر مطابق
  همان ابعاد آپلود می‌کند. (فرمت/حداقل/حداکثر رزولوشن مجاز از پیش مشخص و زیر باکس
  آپلود نمایش داده شود: PNG، ۱۶×۱۶ تا ۵۱۲×۵۱۲.)
- مشخصات نیرو: کاربر ویژگی‌ها را **انتخاب** می‌کند و هرکدام را **مقداردهی**
  (بعضی نیازی به مقدار ندارند). مثال‌ها: hp، damage، نرخ شلیک، range، سرعت، آرمور.
  یک نیرو ممکن است فقط دفاعی باشد (فقط hp+armor، بدون damage) — پس فقط فیلدهای
  انتخاب‌شده نمایش داده شوند.

**تک‌بخشی — تب ارتقا:**
- کاربر تعیین می‌کند نیرو پس از رسیدن به چه **دستاوردی** (نودِ درخت ارتقای HQ /
  تعداد کشته / مقدار زمان / …) ارتقا یابد؛ چه ویژگی‌هایی ارتقا/اضافه شوند.
- تغییر ظاهری پس از ارتقا و حتی تغییر ابعاد — **با سقف سخت +۱۵٪** افزایش ابعاد.

**تک‌بخشی — تب تعلیم:**
- توسط چه ساختمانی، با چه هزینه‌ای، در چه سطحی از درخت ارتقا این نیرو ساخته شود.
  (`from_building`, `cost`, `required_tech` — همه dropdown از موجودیت‌های تعریف‌شده،
  نه متن آزاد.)
- سپس «ذخیره».

**چندبخشی — تب اصلی:**
- گرافیک: کاربر **۳ بخش** انتخاب می‌کند. بخش ۱ = پس‌زمینه، بخش ۲ روی ۱، بخش ۳ روی
  ۲. قانون اندازه: `px(بخش۳) ≤ px(بخش۲) ≤ px(بخش۱)`. برای هر بخش تصویر جدا آپلود.
- مشخصات: برای هر بخش ویژگی‌ها تعریف می‌شود، **اما ویژگی‌ها نباید هم‌گروه/متداخل
  باشند** (جدول سازگاری `stat_registry.compatible`). **نکته‌ی گیم‌پلی:** وقتی در
  بازی کاربر به سطحی از تکنولوژی برسد که بتواند نیروها را **ترکیب** کند، از قابلیت
  همه‌ی بخش‌ها هم‌زمان استفاده می‌کند (پرچم `fusable` فقط برای چندبخشی).

**چندبخشی — تب ارتقا/تعلیم:** مثل تک‌بخشی، با این تفاوت که در ارتقا می‌تواند تعیین
کند **کدام بخش** از نظر ظاهری تغییر کند (سقف +۱۵٪ روی ابعاد بخش پایه/۱).

#### ۴.۷.۲ ویرایشگر ساختمان (Building) — `R8.3`
مشابه نیرو، ولی تب سوم به‌جای «تعلیم» = **«تکنولوژی ساخت»**. تفاوت‌های کلیدی:
- **تک‌بخشی:** مشخصات ممکن است شامل `extraction_rate` باشد (ساختمان منبع).
- **چندبخشی:** هر بخش **اجباراً hp + armor دارد**؛ بقیه‌ی ویژگی‌ها نباید متداخل
  باشند. **نکته‌ی گیم‌پلی:** هر بخش مستقلاً توسط دشمن تخریب می‌شود و ساختمان همان
  ویژگی‌ها را از دست می‌دهد (`part_destructible: true`).
- **تب تکنولوژی ساخت:** با چه هزینه/متریالی و در چه سطح درخت ارتقا ساخته شود.

#### ۴.۷.۳ نتیجه — `R8.4`
پس از این، کاربر یک بلوک نیرو ✅ و یک بلوک ساختمان ✅ ساخته است.

### ۴.۸ Map Editor — `R9`
دو بخش: **object editor** و **map editor**.

#### ۴.۸.۱ Object Editor — `R9.1`
مشابه نیرو/ساختمان (بلوکی + درختی). کاربر ذخیره می‌کند: نام، ابعاد، تصویر؛ **نوع
placement** (دریا / خشکی / هردو)؛ **قابل استخراج بودن**؛ و اگر قابل‌استخراج است،
**چه متریالی** می‌دهد (`yields{material, rate}`).

#### ۴.۸.۲ Map Editor — `R9.2`
- کاربر ابعاد نقشه و یک نام انتخاب می‌کند؛ سپس صفحه‌ی نقشه باز می‌شود.
- **zoom in/out + جابه‌جایی (pan)** در بوم نقشه.
- تعیین **دریا/خشکی** با قلم؛ بازی خودش **مرز دریا/خشکی را اصلاح می‌کند تا
  یکپارچه به‌نظر برسد** (ساحل/beach) — این **فقط رندری** است (`coast_autotile.gd`)،
  داده‌ی منطقی فقط land/sea/wall است.
- افزودن **objectهای تعریف‌شده:** پس از انتخاب object، یک نمونه وسط صفحه می‌آید که
  کاربر جابه‌جایش می‌کند؛ کنار صفحه دو گزینه: **حذف** و **جای‌گذاری**.
- گوشه‌ی صفحه **Save**؛ سپس نقشه در بازی قابل‌استفاده است.

### ۴.۹ چیدمان خودکار HQ/Flag و مدیریت موقعیت — `R10`
- `R10.1` **auto placement:** هنگام استارت، اگر نقشه موقعیت flag/HQ از پیش نداشت،
  موتور موقعیت بازیکنان را خودش تعیین می‌کند.
- `R10.2` گزینه‌ای در منوی شروع: بازیکنان **هم‌تیم نزدیک هم** یا **چینش رندوم**.
- `R10.3` اگر نقشه موقعیت flag/HQ از پیش داشت، کاربر در منوی شروع تعیین می‌کند هر
  بازیکن/AI کجا و هر flag کجا باشد.
- `R10.4` اگر تعداد flag/HQ نقشه کمتر از تعداد بازیکنان/تیم‌ها بود، کاربر تا جای
  ممکن دستی تعیین می‌کند و **مازاد را موتور خودش جای‌گذاری می‌کند**.
- `R10.5` (مود ادیتور) افزودن بخشی برای تعیین **محل flag/HQ** روی نقشه.

### ۴.۱۰ کنترل‌گروه‌ها (Control Groups / یگان‌بندی) — `R11`
- گوشه‌ی صفحه‌ی بازی یک بخش است که با کلیک، صفحه‌ی **۳×۳** (خانه‌های ۱ تا ۹)
  باز می‌کند.
- کاربر یک دسته نیرو را انتخاب می‌کند → روی «یگان‌بندی» → روی یکی از شماره‌ها →
  آن نیروها عضو آن یگان می‌شوند. برای ساختمان‌ها هم مشابه.
- کلیک بعدی روی همان شماره = انتخاب سریع آن یگان.
- **پیاده‌سازی:** کنترل‌گروه‌ها **UI/انتخاب‌اند، نه شبیه‌سازی** — در حالت
  تک‌نفره می‌توانند سمت کلاینت باشند؛ ولی چون انتخاب از طریق `select_units` فرمان
  می‌شود، در مولتی‌پلیر هم سازگار است.

### ۴.۱۱ رابط بازی: عمودی/افقی + مینی‌مپ + پنل نیرو/ساختمان — `R12`
- `R12.1` **هم عمودی و هم افقی** (portrait + landscape) — هرجور گوشی گرفته شد

- `R12.3` **مینی‌مپ** گوشه‌ی صفحه (نمای کوچک کل نقشه + موقعیت دوربین + نیروها).
- `R12.4` دو دکمه‌ی **نیرو / ساختمان**:
  - کلیک روی «نیرو» → لیست نیروهای موجود (قابل اسکرول)؛ کلیک روی هرکدام →
    نمایش **همه‌ی ویژگی‌های تعریف‌شده** برای آن نیرو (hp، damage، نحوه‌ی ارتقا و …).
  - «ساختمان» به‌طور مشابه.

## ۹. قراردادهای داده (Schemaها که نباید بشکنند)

> این‌ها منبع حقیقتِ فرمت داده‌اند. موتور فیلدهای `editor.*` را نادیده می‌گیرد.
> فقط `logical_size` (بر حسب tile) و stat/cost داده‌ی شبیه‌سازی‌اند؛ بقیه cosmetic.

### ۹.۱ درخت ادیتور
```jsonc
"editor": { "parent_id": "root_unit", "tree_order": 3 }
```
ریشه‌های مجازی (در JSON ذخیره نمی‌شوند): `root_unit` / `root_building` / `root_object`.

### ۹.۲ گرافیک پیکسلی
```jsonc
"graphic": {
  "mode": "single",                    // "single" | "multi"
  "logical_size": { "w": 1, "h": 1 },  // TILE — تنها فیلدی که شبیه‌سازی می‌خواند
  "parts": [                           // single=۱ ، multi=حداکثر ۳ لایه (بزرگ‌ترین اول)
    { "layer": 1, "px": {"w":64,"h":64}, "texture": "textures/u_base.png" }
  ]
}
```
قانون: `px(layer3) ≤ px(layer2) ≤ px(layer1)`؛ PNG فقط؛ ۱۶×۱۶ تا ۵۱۲×۵۱۲.

### ۹.۳ مشخصات + سازگاری چندبخشی
گروه‌ها: `combat` (damage/fire_rate/range)، `defense` (hp/armor)، `mobility`
(move_speed)، `economy` (extraction_rate)، `vision`. دو بخش نمی‌توانند stat هم‌گروه
داشته باشند (استثنا: defense برای ساختمان که هر بخش اجباراً hp+armor دارد).
`fusable: true` فقط برای چندبخشی.

### ۹.۴ ارتقا
```jsonc
"upgrade": {
  "trigger": { "type": "tech_node|kill_count|time_ticks|activity", "value": 50, "ref": "tech_x" },
  "effects": { "stat_add": {}, "stat_mul": {}, "add_ability": [] },
  "visual_change": { "part": 1, "texture": "textures/u_lvl2.png", "px": {"w":72,"h":72} }
}
```
سقف سخت: ابعاد جدید بخش پایه ≤ +۱۵٪ اصل.

### ۹.۵ تعلیم/تکنولوژی ساخت
```jsonc
"buildable": { "from_building": "barracks", "cost": {"resource_basic":50},
               "materials": [], "required_tech": "tech_node_id" }
```
همه ارجاعِ id (dropdown)، نه متن آزاد.

### ۹.۶ آبجکت نقشه
```jsonc
{ "id": "iron_rock", "graphic": {...}, "logical_size": {...},
  "placement": "land|sea|both", "extractable": true,
  "yields": { "material": "iron", "rate": 2 } }
```

### ۹.۷ زمین نقشه + سناریو
توکن‌های منطقی: `land` / `sea` / `wall`. ساحل ذخیره نمی‌شود (رندری، از همسایه‌ها).
```jsonc
"map": { "width": 32, "height": 24, "walls": [...], "sea": [[3,3],[4,4]] },
"objects": [ { "object": "iron_rock", "x": 6, "y": 6 } ],
"flags": [ { "index": 0, "x": 4, "y": 7 } ]   // برای CTF/HQ (R10)
```

### ۹.۸ منوی شروع مسابقه (خروجی UI → GameBootstrap)
```jsonc
{ "match_name": "My Battle", "scenario": "skirmish_basic",
  "human_players": 1, "ai_players": 3,
  "game_mode": "team|ffa|ctf",
  "team_layout": "clustered|random",
  "placements": [ { "slot": 0, "kind": "human", "team": 0, "flag_index": 0 } ] }
```

### ۹.۹ فرمت `.nexpack` (بدون تغییر از فاز C)
ZIP شامل `manifest.json` + `data/<catalog>/*.json` + `textures/*.png`، معادل یک
پوشه‌ی `mods/<id>/`. کاتالوگ‌های دلخواه (units/buildings/objects/scenarios/tech)

## ۱۰. اصول طلایی ثابت پروژه (هرگز نقض نکن)

1. **منطق ≠ گرافیک (Cosmetic vs Logic):** هر «پیکسل/تصویر/رنگ/فونت/تم/ساحل/
   انیمیشن/مینی‌مپ/zoom» فقط بصری است و روی هش قطعی اثر ندارد. فقط
   `logical_size`/stat/cost/فرمان داده‌ی شبیه‌سازی‌اند. (با تست «هش بدون تغییر» اثبات
   می‌شود.)
2. **همه‌چیز از EventBus/WorldState:** هیچ ماژول/UI ماژول دیگر را مستقیم صدا نمی‌زند.
3. **Tooling-only:** ادیتورها هرگز به WorldState/هش دست نمی‌زنند؛ فقط داده تولید
   می‌کنند.
4. **Validate-before-save:** هیچ پک/save نامعتبری ذخیره نمی‌شود؛ ورودی نامعتبر با
   دلیل رد می‌شود.
5. **English-only در کد:** طبق `docs/CODE_POLICY.md`؛ متن غیرانگلیسی فقط در
   `localization/`؛ هر متن UI جدید کلید در `en.json` **و** `fa.json` دارد
   (CI با `tools/check_code_policy.gd` چک می‌کند).
6. **Data-Driven بمان:** هر آیتم/ساختمان/تکسچر/نوع‌بازی جدید داده است، نه کدِ
   hardcode.
7. **قطعیت (Determinism):** هر تصمیم شبیه‌سازی باید از `current_tick`/seed/کلیدهای
   مرتب‌شده بیاید، نه از RNG سیستمی یا `delta` واقعی — وگرنه مولتی‌پلیر desync
   می‌شود.
8. **معیار پذیرش = تجربه‌ی کاربر:** «تست headless سبز» کافی نیست؛ قابلیت باید روی
   دستگاه واقعی توسط کاربر دیده و استفاده شود.
