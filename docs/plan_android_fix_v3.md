## ۱. نظرِ تخصصی و تصمیم‌های کلیدیِ طراحی (پیش از فازبندی)

### الف) تناقضِ مسیریابی و مه‌جنگ (درخواست ۱) — مهم‌ترین نکته‌ی گیم‌پلی
کاربر درست تشخیص داده که یک **تناقض** وجود دارد: اگر نیروها همیشه از گرید کاملِ
واقعی (شاملِ دیوارهایی که هنوز کشف‌نشده‌اند) مسیریابی کنند، عملاً «تقلب» می‌کنند و
دیوارِ پنهان را دور می‌زنند. راهِ حلِ استاندارد و قطعی (deterministic):
- مسیریابی روی **گرید «باورِ» بازیکن** (belief grid) انجام شود: تایل‌های
  `VISIBLE`/`EXPLORED` وضعیتِ واقعی‌شان، و تایل‌های `HIDDEN` به‌صورتِ «فرض بر
  walkable» در نظر گرفته شوند.
- وقتی نیرو حین حرکت به مانعِ کشف‌نشده برخورد کرد (تایل تازه `VISIBLE` شد و
  blocked بود) → **مسیر دوباره محاسبه** شود (incremental replan). این همان رفتارِ
  انسانیِ «نمی‌دانستم اینجا دیوار است، دور می‌زنم» است و تقلب نیست.
- این کار باید **قطعی** بماند: belief grid از fog-state مشتق می‌شود که خودش قطعی
  است؛ pathfinding از قبل قطعی است؛ پس replan هم قطعی است.
- **دو حالتِ حرکت:** (۱) «مسیرِ دستی» = کاربر/AI مجموعه‌ای waypoint می‌دهد و نیرو
  دقیقاً از آن‌ها می‌رود؛ (۲) «مستقیم/خودکار» = A* روی belief grid. حالتِ ۱ برای AI
  یعنی برنامه‌ریزِ استراتژیک waypoint می‌دهد.

### ب) نقشه‌ی سه‌حالته (درخواست ۲) — عمدتاً رندر
منطق (`fog_of_war_module`) از قبل سه حالت دارد. کارِ اصلی: در map/minimap یک لایه‌ی
**snapshot «آخرین‌تصویر»** برای تایل‌های `EXPLORED` نگه‌داری و رندر شود (نیمه‌شفافِ
سیاه). این snapshot باید **cosmetic** باشد و روی hashِ قطعی اثر نگذارد.

### ج) دیپلماسی + شخصیت + یادگیری (درخواست‌های ۱۱–۱۶) — چهار لایه‌ی جدا
طبقِ توصیه‌ی درست (که کاربر آورد)، این‌ها را در **چهار لایه‌ی مستقل** می‌سازیم تا
آشوب/اکسپلویت پیش نیاید:
1. **Personality (ثابت):** بردارِ ۳۵ پارامتری (personality/strategy_bias/
   diplomacy_bias/learning_bias/difficulty). با بازی reset نمی‌شود.
2. **Relationship/State (پویا، درون‌بازی):** وضعیتِ رابطه (بی‌طرف…هم‌پیمان) +
   امتیازهای لحظه‌ای (ترس، اعتماد، خشم…). با پایانِ بازی reset می‌شود.
3. **Diplomacy actions:** پیام‌های ساختاریافته (قرارداد) + چتِ متنی؛ تصمیمِ AI از
   یک تابعِ سود/هزینه‌ی قطعی می‌آید.
4. **Reputation/Memory (ماندگار بینِ بازی‌ها، جدا از personality):** سابقه‌ی
   پیمان‌شکنی/کمک برای هر جفت‌بازیکن؛ ذخیره در `user://`.
- **بدون سقفِ سختِ اتحاد**، اما با **هزینه‌ی سیاسی** (اعتمادِ متحدهای دیگر کم شود).
- **قطعیت:** همه‌ی تصمیم‌های AI باید از worldstate + tick + profile مشتق شوند (بدونِ
  RNGِ غیرseeded)، وگرنه lockstep می‌شکند. پیام‌ها Commandهای قطعی‌اند.
- **دادنِ نیرو:** انتقالِ کاملِ مالکیت نه؛ به‌جایش «فرمانِ مشترک» یا «اعزامِ موقت»
  (نیرو مالِ خودش می‌ماند). این هم واقعی‌تر است هم اکسپلویت‌پذیر نیست.

### د) سختی = کیفیتِ تحلیل، نه حذفِ خطا (درخواست ۱۵)
سختی روی: دقتِ ارزیابی، سرعتِ واکنش، عمقِ برنامه، و **درصدِ خطای غیرمجبور** اثر
بگذارد. حتی در سخت‌ترین حالت `minimum_unforced_error_percent > 0`. خطاها باید از یک
منبعِ **seeded** بیایند (مثلاً hash(tick, owner, match_seed)) تا قطعیت حفظ شود.

### ه) چیزهایی که «کدزن نمی‌تواند بسازد» → پرامپت برای AIِ طراح
آیکن‌ها (۳) و اسپرایتِ انیمیشن‌ها (۵) و آبجکت‌های تصویری، تصویر/گرافیک‌اند نه کد.
فاز MC3 و بخشی از MC4 خروجی‌شان یک **سندِ پرامپتِ دقیق** (`docs/ASSET_PROMPTS_fa.md`)
است: برای هر آیکن/انیمیشن، فرمت (PNG با آلفا / sprite-sheet)، ابعادِ px، تعداد
فریم، نام‌گذاری، و محلِ قرارگیری در پروژه مشخص می‌شود تا کاربر به AIِ طراح بدهد.
کد فقط **جای این assetها را آماده** می‌کند (data-driven) تا بعدِ دریافت، صرفاً فایل
جایگزین شود.

### و) قطعیت و جداسازیِ منطق/رندر (تکرارِ اصولِ ثابتِ پروژه)
همه‌ی چیزهای «تصویری» (آیکن، انیمیشن، لایه‌ی discovered، GUIِ داده‌محور، پس‌زمینه‌ی
ویدئویی) باید **cosmetic** باشند و در `state_hasher` اثر نگذارند. هر چیزی که روی
شبیه‌سازی اثر دارد (مسیر، دیپلماسی، نیرو) از طریقِ **Command** و **قطعی** است.

## فاز MC1 — حرکتِ نیرو: دو حالته + مسیریابیِ آگاه‌از‌مه‌جنگ (درخواست ۱) ✅ (انجام شد)

**هدف:** رفعِ تناقضِ مه‌جنگ و افزودنِ حرکتِ «مسیرِ دستی» و «مستقیم».

- **MC1.1:** یک utilِ خالصِ `core/belief_grid_util.gd` (RefCounted) که از map-grid +
  fog-state یک «گریدِ باور» می‌سازد: `HIDDEN` → فرضِ walkable، `VISIBLE/EXPLORED` →
  واقعیت. قطعی و بدونِ SceneTree. + تست‌های headless.
- **MC1.2:** `core/path_service.gd` — یک تابعِ `find_path_on_belief(...)` که روی
  belief grid مسیر می‌دهد (بازاستفاده از A*). + تست.
- **MC1.3:** `modules/units/units_module.gd` — «replan on contact»: وقتی نیرو در حرکت
  به تایلی رسید که تازه `VISIBLE` و blocked شد، مسیر را روی belief جدید بازمحاسبه کند
  (قطعی). + تست.
- **MC1.4:** حالتِ «مسیرِ دستی»: پشتیبانی از فرمانِ `move_unit` با آرایه‌ی
  `waypoints` (به‌جای یک goal). نیرو دقیقاً از waypointها می‌رود. util +
  `units_module` + تست.
- **MC1.5:** رابطِ کاربری در `ui/mobile/game_hud.gd` + `ui/desktop/desktop_hud.gd`:
  یک تاگلِ «مسیرِ دستی/مستقیم»؛ در حالتِ دستی، tapهای متوالی waypoint اضافه می‌کنند و
  یک tapِ تأیید فرمان را صادر می‌کند. (منطقِ خالص در util، UI فقط Command صادر کند.)
- **MC1.6:** i18n (کلیدهای `ui.move.*`) + تست‌های localization + commit/push.

**نکته‌ی قطعیت:** replan فقط وقتی رخ می‌دهد که fog-state (که قطعی است) تغییر کند؛ پس
همه‌ی peerها یکسان replan می‌کنند.

## اصولِ ثابتِ هر مرحله (Definition of Done)

یک مرحله فقط وقتی «تمام» است که همه‌ی این‌ها برقرار باشد:
1. کد نوشته/ویرایش شده و **ASCII خالص** است (CODE_POLICY).
2. منطق در یک utilِ خالصِ `RefCounted` قابلِ‌تستِ headless است (UI فقط Command).
3. تستِ headless اضافه و در `tests/test_runner.gd` ثبت شده و **کلِ مجموعه سبز** است
   (پایه `1301/1301`؛ با هر فاز بالاتر می‌رود).
4. i18n: هر متنِ نمایشیِ جدید کلیدِ ترجمه دارد (fa/en).
5. **قطعیت:** هیچ تغییری روی `state_hasher` جز از راهِ Command؛ چیزهای تصویری
   cosmetic‌اند.
6. `git add + git commit + git push` بلافاصله انجام شده (چک‌پوینت).
